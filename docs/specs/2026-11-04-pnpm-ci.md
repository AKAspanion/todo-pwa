# Switch CI and deploy to pnpm

Date: 2026-11-04 · Status: approved (self-approved on settled facts)

## 1. Why

The developer moved the repository to pnpm: `pnpm-lock.yaml` and `pnpm-workspace.yaml` at the root and in
`functions/`, `packageManager: pnpm@12.16.1` in `package.json`, and both `package-lock.json` files deleted. The CI
and deploy workflows still run `npm ci`, which fails with no `package-lock.json`.

The migration also dropped the security overrides. pnpm doesn't read npm's `overrides` key in `package.json`, so
the new lockfiles resolve the vulnerable versions those overrides lifted (for example `gaxios` → `uuid@9.0.1`, where
the override asks for `^11.1.1`). `pnpm audit --prod --audit-level moderate` reports one high `@grpc/grpc-js`
advisory at the root and two moderate `glob` advisories in `functions/`, so the shipped-dependency audit gate
([quality/ci](../../knowledge/quality/ci.md)) would fail.

## 2. Goal

Every job in `ci.yml` and `deploy.yml` installs and runs with pnpm, at the version `packageManager` names, and
keeps every gate it has today, with the audit passing for the same reason as before.

## 3. Design

**Installing pnpm.** In each job, `pnpm/action-setup` comes before `actions/setup-node`. It's pinned to a commit
SHA, like every action here (`docs/SECURITY.md`), at `v6.1.0`: `v6.1.1` came out the day before this change.
With no `version` input, it reads `packageManager` from `package.json`, so the version lives in one place.
`setup-node` then uses `cache: pnpm`, with `cache-dependency-path` naming the `pnpm-lock.yaml` files the job
installs.

**Commands** (`ci.yml` and `deploy.yml`):

| npm today | pnpm |
| --- | --- |
| `npm ci` | `pnpm install --frozen-lockfile` |
| `npm --prefix functions ci` | `pnpm --dir functions install --frozen-lockfile` |
| `npm run <x>` / `npm --prefix functions run <x>` | `pnpm run <x>` / `pnpm --dir functions run <x>` |
| `npm audit --omit=dev --audit-level=moderate` | `pnpm audit --prod --audit-level moderate` |
| `npx playwright …`, `npx firebase …` | `pnpm exec playwright …`, `pnpm exec firebase …` |
| cache keys on `hashFiles('package-lock.json')` | `hashFiles('pnpm-lock.yaml')` |

`functions/` is its own pnpm workspace root (its own `pnpm-workspace.yaml` and lockfile), so `--dir functions` installs it
apart from the root, as `--prefix functions` did.

**Deploy key rule** ([operations/deploy](../../knowledge/operations/deploy.md)): every install still runs
before any step that holds the key, with `--ignore-scripts`. The hosting action's own `npx firebase-tools`
install keeps `npm_config_ignore_scripts`. `firebase.json`'s functions predeploy (`npm --prefix … run build`)
only runs a `package.json` script, which works over a pnpm `node_modules`, so it stays as it is.

**Overrides.** Each npm override moves to `overrides:` in the matching `pnpm-workspace.yaml`, written in pnpm's
`parent>child` form (`'gaxios>uuid': ^11.1.1`), and leaves `package.json`, so it's stated in one place only. Both
lockfiles are regenerated. Success: `pnpm audit --prod --audit-level moderate` exits 0 at the root and in
`functions/`.

**Docs.** The lines in `docs/SECURITY.md` and `README.md` that describe what CI and deploy run, and the
[quality/ci](../../knowledge/quality/ci.md) and [operations/deploy](../../knowledge/operations/deploy.md)
concepts, name the pnpm commands and where the overrides now live.

## 4. Non-goals

- The README's local-development commands (`npm install`, `npm run dev`, …), `playwright.config.ts`'s
  `npx vite` and `.github/dependabot.yml`. Dependabot's `npm` ecosystem reads pnpm lockfiles, and `npx`
  resolves `node_modules/.bin`. These don't break CI, and they're for a separate follow-up.
- `codeql.yml` installs nothing.

## 5. Testing

No unit test can run a workflow. What gets checked:

- `pnpm install --frozen-lockfile` succeeds at the root and in `functions/` after the lockfiles are regenerated.
- `pnpm audit --prod --audit-level moderate` exits 0 in both.
- The pnpm commands each job runs work locally (lint, typecheck, format check, build, functions build and lint).
- No `npm ci` or `npm audit` is left in the workflows, and every new `uses:` is pinned to a full SHA.
- The real proof is the pull request's CI run.
